# Mochi 3.0 review — what to carry forward

> Reviewed 2026-07-26 from `archive/mochi-3.0/`. Nothing implemented.
> Purpose: decide what 3.0 got right, before rewriting Mochi as a
> JaegerOS app.

## Where Mochi actually is

| | What it is | Verdict |
|---|---|---|
| **3.0** (`archive/mochi-3.0/`) | A standalone node-based animation middleware. Broker, node base, plugin registry, ZMQ transport, three plugins. | **Clean. The reference.** |
| **4.0** (`mochi/`, branch `mochi-v4`) | A JROS 0.5.0-era monorepo fork — agent, app, cli, core, hardware, interfaces, nodes, personality, plugins, skill_tree, timeline, transport, all vendored in. | **Bloated and stale.** Its agent is far behind JaegerAI 0.9.6; its framework predates Phase U, the four-way split, and the module system. |

4.0 is what the split exists to prevent: everything locked into one app,
so the agent could not be updated without updating the app. That is
precisely the problem module-per-repo solves.

**3.0 is the shape 4.0 should have grown into.**

## What 3.0 got right

**The whole core is 997 lines.**

```
core/broker.py           46   XPUB/XSUB forwarder
core/node_base.py       285   the node contract
core/plugin_registry.py  91   discovery + subprocess lifecycle
core/topics.py           80   topic vocabulary + node catalog
core/zmq_manager.py      64   sockets
core/messages.py         49
core/host_monitor.py    123
main.py                 210   the supervisor
```

### 1. Nodes announce themselves — introspection, built in

Every node publishes a META payload on startup:

```python
{"schema": "mochi.node.meta.v1",
 "node_id": ...,
 "required_topics": [...],
 "optional_topics": [...],
 "addresses": {"pub_frontend": ..., "ctrl": ...}}
```

**This is the single biggest thing to carry back.** It is the "tag
registry / live bus catalog" gap ranked **#2** in
`20260726_ros_parity_review.md` — the biggest ergonomics gap versus ROS,
where `ros2 topic list/info` is table stakes. JaegerOS has no way to ask
a running system what is publishing what. 3.0 had it, and it cost ~10
lines because every node already knew its own topics.

### 2. Health carries real telemetry, in the BASE class

```python
{"schema": "mochi.node.health.v1",
 "fps_target": ..., "memory_mb": ..., "tx_rate_mbps": ...,
 "sequence": ...}
```

Every node, automatically, no per-module work. Compare: JaegerOS's
`NodeHealth` carries `state` + a `detail` string and no severity, and I
hand-built `/sense/animation_stats` for ONE module last week. 3.0's
approach is better — **telemetry belongs in the node base, not in each
module** — and it covers parity gaps 2a and 2c at once.

### 3. Nodes are processes, on/off by config

```yaml
plugins:
  - id: animation
    module: plugins.animation_node.node
    cwd: plugins/animation_node
    config_path: plugins/animation_node/config.yaml
    enabled: true
```

`main.py` filters `spec.enabled`, spawns each as a subprocess, polls,
terminates on shutdown. JaegerOS's `jaeger.toml` has the same `enabled`
flag, so the *declaration* is at parity — but 3.0 gets true process
isolation, where JaegerOS's `fused` mode runs everything in one process
and one bus delivery thread (the measured 541 ms head-of-line stall).

Worth being honest about the trade: fused mode is why in-process frames
cost nothing (reference passing). 3.0 paid serialization for isolation.
Neither is simply better — but 3.0 proves the framework can support
both, and JaegerOS today effectively supports one.

### 4. Schema-versioned payloads

`mochi.node.health.v1`, `mochi.node.meta.v1`. Versioned from the start,
so a consumer can refuse a payload it does not understand.

### 5. `_render_tick() -> memoryview`

Frames return as a `memoryview`, not `bytes` — zero-copy out of the
render buffer. JaegerAnimation currently does `rgba.tobytes()` per frame,
a full copy at 600 KB/frame for a desktop face.

## What 3.0 got wrong (do not carry these)

- **Plugins are launched by dotted module path + cwd + config_path from
  a root config.** That is a hardcoded registry: the host must know every
  plugin's import path. JaegerOS's entry-point discovery is strictly
  better — a module installs itself and the framework never names it.
- **No slot concept.** Plugins are identified by id and type, so swapping
  a TTS engine means editing the host config, not installing a different
  package.
- **Topics are byte-prefixed strings** (`build_topic("ext","stt","text")`)
  with no schema behind them. JaegerOS's msgspec contract is a real
  improvement.
- **`gui/` is a plugin.** A face is a subscriber, not a node.

## Still open — and #8 is load-bearing

**7 — frames are copied twice.** `MathAdapter` does `rgba.tobytes()`,
then the node does `bytes(frame.data)` again into `AnimationFrame`. 3.0
returned a `memoryview` straight out of the render buffer. At 600 KB per
desktop frame that is two full copies per frame, 30 times a second.

**8 — nothing outside the process can ask anything.** This is the piece
I missed on the first pass, and it is bigger than it looks.

`core/host_monitor.py` (123 lines) subscribes to the broker, caches
health/meta/last-event per node, and exposes a **ZMQ REP socket for
queries**. `tools/monitor_cli.py` and `gui/control_cli.py` are separate
processes that connect to it — to inspect state, and to send commands to
individual nodes.

`BusCatalog` (built here) is only half of that: it is an **in-process**
subscriber. To use it today you must be inside the app. There is no way
for a CLI, a GUI, or an operator on another terminal to ask a running
JaegerOS system anything, or to tell a node to do something.

That is precisely what Mochi 5.0 is supposed to demonstrate — "test
nodes, turn things on and off, send commands to each node". The
in-process half is done; the external half is not built.

It also completes parity gap 1b properly: a bus catalog nobody can query
from outside is not the `ros2 topic list` equivalent, it is half of it.

## The Mochi rewrite

**Scope:** a Grok-companion-style JaegerOS app — what 3.0 did, refined,
composing modules instead of vendoring a framework.

```
Mochi (new branch, from empty)
├── jaeger.toml          app manifest — nodes, surfaces, bus
├── mochi/
│   ├── __init__.py
│   └── surfaces/window.py   PySide6 face — a bus SUBSCRIBER, not a node
├── content/
│   └── characters/          character packs (emotes ships in JaegerAnimation)
├── requirements.txt     pins jaeger-os + jaeger-animation
└── dev/tests/
```

Pins, does not vendor: `jaeger-os` (framework), `jaeger-animation`
(the `animation` slot). JaegerAI is added later — animation-only first,
per the earlier decision, so a failure has one place to be.

Nothing from `mochi/` (4.0) is carried over. `mochi-v4` keeps it as
history.

**First milestone:** `./launch` opens a window, the animation node boots
from the manifest, and the `emotes` character renders — proving the app
format and module composition end to end with the smallest surface that
can prove anything.
